# Swift queries and normalized entities compared with TanStack DB

## Resolve a list and a detail view through the same stack

A screen needs the open todos for project 42 and the todo with ID 7. The app models each todo and its assignee as a class. Two todos assigned to the same person reference the same object, so a view can read `todo.assignee?.name` directly. The app defines `TodoByID`, `OpenTodos`, and `OpenTodoList` and runs the queries through a `DBStack`.

```swift
import StateGraphSync

struct TodoByID: Query {
  let id: Todo.TypedID
  @DBDependency private var data: TodoData?

  func perform() async throws -> Todo? {
    let data = try $data.require()
    return try await data.todo(by: id)
  }
}

struct OpenTodos: Query {
  let projectID: Int
  @DBDependency private var data: TodoData?

  func perform() async throws -> OpenTodoList {
    let data = try $data.require()
    let list = await OpenTodoList(projectID: projectID, data: data)
    try await list.loadNext()
    return list
  }
}

// Call from the view on @MainActor. Resolving the list loads its first page.
let list = try await stack.query(OpenTodos(projectID: 42))
let firstRows: [Todo] = list.rows
if list.hasNextPage {
  try await list.loadNext()
}
let detail: Todo? = try await stack.query(TodoByID(id: .init(7)))
```

The return type of `perform()` determines `Query.Output`. The detail query returns a reference to the same `Todo` the list holds by ID. The list query returns a handle that can load more pages. An app that needs a count can define another query whose `perform()` returns an `Int`.

### Model the relationship and merge API responses

The API client returns value payloads. Each todo payload contains its ID, title, and either a complete assignee payload or an explicit null for an unassigned todo. The app owns one `EntityStore<Todo>` and one `EntityStore<Assignee>` for the session. Each store keeps one class instance per ID. `@GraphStored` tracks changes to both the relationship and the fields on its target.

```swift
import StateGraph
import StateGraphNormalization

nonisolated final class Assignee: TypedIdentifiable, Sendable {
  typealias TypedIdentifierRawValue = Int
  let typedID: TypedID
  @GraphStored var name: String

  @InitAndUpdate
  init(payload: AssigneePayload) {
    #onInit { self.typedID = payload.id }
    self.name = payload.name
  }
}

nonisolated final class Todo: TypedIdentifiable, Sendable {
  typealias TypedIdentifierRawValue = Int
  let typedID: TypedID
  @GraphStored var title: String
  @GraphStored var assignee: Assignee?

  @InitAndUpdate
  init(payload: TodoPayload, assignee: Assignee?) {
    #onInit { self.typedID = payload.id }
    self.title = payload.title
    self.assignee = assignee
  }
}
```

The detail and page loads both call this method on `TodoData` after a successful read. It resolves the assignee first, then stores that reference on the todo. `updateOrCreate` finds the instance by ID, and the `update` method generated by `@InitAndUpdate` applies the incoming fields in place.

```swift
func merge(_ row: TodoPayload) -> Todo {
  let assignee = row.assignee.map { payload in
    assignees.updateOrCreate(
      id: payload.id,
      update: { $0.update(payload: payload) },
      create: { Assignee(payload: payload) }
    )
  }
  return entities.updateOrCreate(
    id: row.id,
    update: { $0.update(payload: row, assignee: assignee) },
    create: { Todo(payload: row, assignee: assignee) }
  )
}
```

A detail view can hold its `Todo` across refreshes. Reading the relationship in `body` tracks both `assignee` and the current assignee’s `name`.

```swift
struct TodoDetail: View {
  let todo: Todo

  var body: some View {
    LabeledContent(todo.title, value: todo.assignee?.name ?? "Unassigned")
  }
}
```

If a response for a different todo renames their shared assignee, this detail view sees the new name. If the server reassigns this todo, the next read follows the new assignee. An explicit null clears just this relationship. Each confirmed response is applied in a synchronous `withGraphTransaction` so observers see the updated fields and list membership together.

### Set up a shared API client and store

```swift
@MainActor
func makeStack(api: any TodoAPI) -> DBStack {
  DBStack(adapter: TodoData(api: api))
}
```

`query(_:)` and `mutate(_:)` make the stack's adapter available to `@DBDependency` while `perform()` runs. The property reads the adapter by its type. Call `try $data.require()` to throw `DBStack.MissingDependency` when that type is unavailable. Build the stack at launch or sign-in and share it across screens.

| Operation | How the app resolves it |
| --- | --- |
| `query(TodoByID(id:))` | Look up `TodoData.entities[id]` first. A previous list request may already have loaded the row. On a miss, call `GET /todos/{id}` and add the row to the same `EntityStore<Todo>`. A service with only a list endpoint can search its pages. It can report a missing ID once it has exhausted every page that could contain it. |
| `query(OpenTodos(projectID:))` | Create a handle and fetch the first page from `GET /projects/{id}/todos?status=open`. Add the rows to the shared store and keep their IDs in display order on the handle. |
| `list.loadNext()` | Follow the server cursor using the same project and filters. If an ID appears again, update its row and keep its original position in the list. A failed call can retry from the same cursor. |

Each handle tracks its own position. Resolving the same query again starts at the first page. Both handles read the current rows from the shared store, and detail lookups reuse any row already there. The app chooses cache expiration and page reuse across queries. The handle’s `@GraphStored` IDs track list membership. The entities’ own `@GraphStored` properties track their fields and relationships. The app imports StateGraph for these observable models. The `StateGraphSync` product provides `DBStack` and includes the `StateGraphNormalization` module for `EntityStore`. ### Pagination in TanStack DB

| Responsibility | Swift example | TanStack DB |
| --- | --- | --- |
| View | Read `list.rows` and `hasNextPage`, then call `loadNext()`. | `useLiveInfiniteQuery` exposes `data`, `hasNextPage`, and `fetchNextPage()`. Fetching the next page extends the window of an ordered live query. |
| API requests | `OpenTodoList` keeps the project ID and next cursor and passes them to the API client. | An on-demand collection’s `queryFn` maps filters and ordering to the API. `createCursorPager` follows backend cursors until it can satisfy the requested offset and limit. |
| Cached data | Each handle keeps its ordered list of loaded IDs. The stack shares entities across handles. | A `QueryClient` can retain pages. The page key includes the project, filters, and ordering so a larger window can reuse the same sequence. |

In the Swift example, each `loadNext()` fetches one server page. Even an empty page can have a continuation cursor. TanStack DB also supports local queries, fetching enough pages to satisfy an arbitrary window, and managing cache freshness. [useLiveInfiniteQuery](https://tanstack.com/db/latest/docs/framework/react/reference/functions/useLiveInfiniteQuery) · [createCursorPager and opaque cursors](https://tanstack.com/db/latest/docs/collections/query-collection#endpoints-with-opaque-cursors)

## A partially loaded social feed

Open **Ranked feed** in the Development app. Home and Marina’s profile both show the ferry post. Load more on the profile, then switch to Home and pull to refresh. Home receives a new first page and an updated like count. Switch back to the profile to see the new count on the same post, with the previously loaded profile rows still in place.

```swift
let home = try await stack.query(FeedQuery(scope: .home))
let firstPost = home.entries.first?.post
try await home.loadNext()
try await home.refresh()
```

| Owner | Data it holds |
| --- | --- |
| Feed service | Membership, ranking, placement IDs, and the meaning of each cursor. The demo uses an in-process service that returns one page per call. |
| Each `FeedTimeline` | The ordered placements loaded for one scope, including display reasons such as “Suggested for you”, and the private cursor for the next request. A missing cursor on a successful page means this sequence has ended. |
| Shared `FeedSession` | One `FeedPost` and one `FeedAuthor` per encountered ID. Both screens can read `post.author.name`. A later response updates those objects in place. |

A feed can include the same post in two different placements. When appending a page, the timeline merges its entities and appends each new placement ID once. Absence from a page gives the client no evidence that a post was deleted. A retained detail view can still use `firstPost` after it leaves Home. This demo retains encountered entities in memory for the lifetime of the feed screen’s session. A long-lived app can choose a shorter retention policy for entities no screen uses.

Each timeline owns an `AsyncDataStore` from the `StateGraphAsyncDataStore` product. Its value holds the placements and next cursor, and its phase tells the view when a page is loading. `loadNext()` submits an action with `.discard`, so repeated taps during a load fetch only one page. `refresh()` uses `.dropCurrent`. Try tapping **Load more** on Home and immediately pulling to refresh. The store cancels the append and starts the replacement after the old handler returns. A transport that ignores cancellation can delay the first-page request.

Refresh sends no cursor and keeps the displayed page until the request succeeds. The handler stages the placements and cursor with `context.update`. If the store accepts the update, the handler merges the page’s posts and authors in the same graph transaction. A cancelled handler cannot publish a late page. A failed refresh preserves the previous continuation for retry. Home and profile run separate stores, so each post and author also checks the service’s snapshot revision before accepting fields from either timeline.

### The same Home and profile feeds in TanStack DB

For the Development demo, use a session-wide collection for posts, another for accounts, and one placement collection per timeline. Each placement has its own ID, references a post by ID, and records the position and reason supplied by the feed service. Two placements of the same post can appear in the same timeline. A live query joins the loaded rows and orders them by placement position. The React view can subscribe with `useLiveQuery(session.home.feed)`. [TanStack DB live queries](https://tanstack.com/db/latest/docs/guides/live-queries)

```ts
import {
  BasicIndex, createCollection, createLiveQueryCollection, eq, localOnlyCollectionOptions,
} from '@tanstack/react-db'

type Post = { id: string; authorId: string; caption: string; likes: number; revision: number }
type Account = { id: string; name: string; revision: number }
type Placement = { id: string; postId: string; position: number; reason: string | null }

function table<T extends { id: string }>() {
  return createCollection(localOnlyCollectionOptions({ getKey: (row: T) => row.id }))
}

export function createFeedSession() {
  const posts = table<Post>()
  const accounts = table<Account>()
  posts.createIndex(p => p.authorId, { indexType: BasicIndex })

  function timeline() {
    const placements = table<Placement>()
    placements.createIndex(p => p.postId, { indexType: BasicIndex })
    const feed = createLiveQueryCollection(q => q
      .from({ slot: placements })
      .innerJoin({ post: posts }, ({ slot, post }) => eq(slot.postId, post.id))
      .innerJoin({ author: accounts }, ({ post, author }) => eq(post.authorId, author.id))
      .orderBy(({ slot }) => slot.position, 'asc')
      .select(({ slot, post, author }) => ({
        id: slot.id, reason: slot.reason, caption: post.caption,
        likes: post.likes, author: author.name,
      })))
    return { placements, feed }
  }

  return { posts, accounts, home: timeline(), profile: timeline() }
}
```

The collections above hold the rows the app has received. The following page-loading policy reproduces the Swift demo. The app implements it for each timeline.

1. **Load more.** The Home loader calls its Home endpoint with Home’s last successful cursor. The profile loader calls the profile endpoint with its own cursor. Capture the timeline’s generation before sending each request. When a page returns for the current generation, merge accounts and posts by ID and revision, append previously unseen placement IDs with positions in server order, and save the returned cursor. A successful page with `nextCursor: null` ends that sequence.
2. **Pull to refresh.** Advance Home’s request generation and fetch its first page without a cursor. Keep the displayed rows and cursor while the request runs. Check the generation before writing *any* collection, including shared posts and accounts. On success, apply the newer entity fields, replace Home’s placements, and install its new cursor. A failure leaves the previous page and continuation available for retry.
3. **Return to the profile.** Updating the ferry post from 29 to 30 likes updates both joined results. Removing the tide-pool placement from Home leaves its post and profile placement intact. The profile still shows ferry, tide pools, and trail in that order.

**Where the built-in pager fits.** TanStack DB also documents a window-based approach. `useLiveInfiniteQuery` requests more rows of an ordered live query. An on-demand Query Collection’s `queryFn` can configure a pager with `createCursorPager({ queryClient, queryKey, fetchPage })` and call `pager.read({ offset, limit }, signal)` to fulfill that window from an opaque-cursor endpoint. Give Home and each profile a distinct page-cache key including the viewer, feed scope and ordering. The pager keeps the server pages and their cursors in TanStack Query’s `QueryClient`. A window can require several HTTP pages, including a lookahead row for `hasNextPage`. [Infinite query hook](https://tanstack.com/db/latest/docs/framework/react/reference/functions/useLiveInfiniteQuery) · [Opaque-cursor adapter and key design](https://tanstack.com/db/latest/docs/collections/query-collection#endpoints-with-opaque-cursors)

The refresh behavior differs. A stale pager read rebuilds the previously loaded pages starting at page one. `pager.reset()` discards the cached sequence for that key, and a row-query refetch can still reuse fresh cursor pages. For the demo’s rule “replace Home with just the first page on success, keep its old cursor on failure,” the explicit per-timeline loader above controls when the new sequence becomes visible. Normalizing a nested REST payload and choosing the Home or profile endpoint are also application decisions. [Refreshing or cancelling a cursor sequence](https://tanstack.com/db/latest/docs/collections/query-collection#refresh-or-cancel-the-sequence)

## Complete a todo with TanStack DB

Create one collection per project and pass it to the React list and detail views. Include the project ID in both the URL and the query key. The `queryFn` below translates the screen’s `completed == false` filter into `status=open`. The example assumes the API returns all todos for the project on an unfiltered request. For pagination, also translate the requested window into API parameters.

```tsx
import { QueryClient } from '@tanstack/query-core'
import { createCollection, createOptimisticAction, eq, useLiveQuery } from '@tanstack/react-db'
import { parseLoadSubsetOptions, queryCollectionOptions } from '@tanstack/query-db-collection'

type Todo = { id: number; title: string; completed: boolean }

export function projectTodos(projectID: number, queryClient: QueryClient) {
  const todos = createCollection(queryCollectionOptions({
    queryClient,
    queryKey: ['projects', projectID, 'todos'],
    getKey: (todo: Todo) => todo.id,
    syncMode: 'on-demand',
    queryFn: async ({ meta, signal }): Promise<Todo[]> => {
      const { filters } = parseLoadSubsetOptions(meta?.loadSubsetOptions ?? {})
      const open = filters.some(f =>
        f.field.join('.') === 'completed' && f.operator === 'eq' && f.value === false
      )
      const path = `/projects/${projectID}/todos${open ? '?status=open' : ''}`
      const response = await fetch(path, { signal })
      if (!response.ok) throw new Error(`GET ${path}: ${response.status}`)
      return response.json()
    },
  }))

  const complete = createOptimisticAction<number>({
    onMutate: id => {
      todos.update(id, draft => { draft.completed = true })
    },
    mutationFn: async id => {
      const response = await fetch(`/todos/${id}/complete`, { method: 'POST' })
      if (!response.ok) throw new Error(`POST complete: ${response.status}`)
      await todos.utils.refetch()
    },
  })
  return { todos, complete }
}
```

```tsx
import { useState } from 'react'

function OpenTodos({ model }: { model: ReturnType<typeof projectTodos> }) {
  const [error, setError] = useState<string>()
  const { data, isLoading, isLoadingError } = useLiveQuery(q =>
    q.from({ todo: model.todos }).where(({ todo }) => eq(todo.completed, false))
  )
  if (isLoadingError) return <p>Could not load the list.</p>
  if (isLoading) return <p>Loading…</p>

  async function complete(id: number) {
    setError(undefined)
    try {
      await model.complete(id).when('settled')
    } catch {
      setError('Could not confirm completion.')
    }
  }
  return <>
    {error && <p>{error}</p>}
    {data.map(todo =>
      <button key={todo.id} onClick={() => complete(todo.id)}>{todo.title}</button>
    )}
  </>
}
```

Create the model with `const model = projectTodos(42, queryClient)` and render `<OpenTodos model={model} />`. TanStack Query’s `queryKey` identifies the fetch cache entry. The TanStack DB live query describes the conditions to apply to the collection’s rows.

The TypeScript examples were type-checked with `@tanstack/react-db 1.0.0-rc.1.5`, `@tanstack/query-db-collection 1.5.2`, and `@tanstack/query-core 5.108.2`. A live query and mock API verified the optimistic update and the refetch after confirmation.
